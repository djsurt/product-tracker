Module 1 · 12 min

Tell the project story

After this module, you can introduce Deal Hunter as a concrete product and accurately frame your contribution.

Start with the user problem

People compare listings manually, miss price drops, and cannot easily see whether a deal is good. Deal Hunter makes a wishlist, searches multiple price sources, records price history, and alerts the owner when a rule is met.

Explain phased delivery

The repository grew from a FastAPI, PostgreSQL, and Redis scaffold through auth and CRUD, a Celery pipeline, sources and caching, alerts, a server-rendered UI, screenshot intake, MCP, server-sent events, and an optional 3D preview. That sequence keeps each phase runnable and demoable.

Frame contribution honestly: say what you built, learned, or would improve; do not invent a team size, ownership role, production traffic, or business metric.

Practice the opening

30-second pitch: “Deal Hunter is a price-tracking wishlist. A FastAPI API stores each user’s products, Celery workers collect offers through a shared source interface, and PostgreSQL keeps price history so the app can show a best deal and send alerts.”

60-second pitch: Add that slow provider work is off the request path, Redis coordinates the queue, cache, and locks, and the UI, MCP endpoint, and deployment demonstrate how the same core model can serve several interfaces.

Practice constraint: be precise, not grand

A strong interview story names the user, the system boundary, and a trade-off. It does not turn a learning project into an invented production success story.

Recall

Why did you build it? Answer with the user’s comparison-and-alert problem, then name the technical learning goal rather than claiming unmeasured impact.

Summary

Lead with the problem, describe phased delivery, and make every contribution claim traceable to the repository.

Module 2 · 16 min

Trace the system architecture

After this module, you can map responsibilities and trace an offer from a user action to stored price history.

Responsibility map

The browser calls FastAPI. FastAPI authenticates, validates, and persists user intent in PostgreSQL; Redis carries Celery work. Celery Beat schedules sweeps, workers call source adapters, and workers append price observations before notification work can react to a drop.

Add and refresh flows

Adding a product stores a query and enqueues discovery. A source implementation satisfies the PriceSource protocol and returns a NormalizedOffer; discovery upserts the resulting offers. A refresh later fetches a known offer, records a price point, updates its cheap last_price snapshot, and may publish a price-drop event.

The API stays thin because provider calls are slow and unreliable. Keeping them in workers protects request latency and lets queue retries absorb transient problems.

Trade-off: one adapter contract

PriceSource makes mock, API, and scraper adapters interchangeable at the pipeline boundary. It does not make providers equally reliable; each still has its own rate limits, fields, and failure behavior.

Recall

Trace one price update: schedule or refresh, Redis broker, Celery worker, source fetch, NormalizedOffer, offer update, PricePoint, then any alert path.

Summary

FastAPI owns fast user-facing operations; workers own source I/O; PostgreSQL owns durable product and price state.

Module 3 · 14 min

Model products, offers, and price history

After this module, you can explain the database choices behind a trustworthy price timeline.

Entities and identity

User owns TrackedProduct rows; a product has many Offer rows; each offer has many PricePoint rows. Alerts, click events, API tokens, dead letters, and a generated 3D model support the main path. UUID primary keys avoid sequential identifiers, and server timestamp defaults let the database provide a shared clock.

Money and integrity

Money uses SQL Numeric and Python Decimal, not float, so values such as 19.99 compare predictably. The unique constraint on product, source, and source-side id makes discovery idempotent. The history index on offer id and observed time supports price-range reads.

History versus snapshot

PricePoint is append-only source of truth for charts and lowest-in-window logic. Offer.last_price is a denormalized snapshot that makes common reads cheaper. Today numerical comparison assumes active sources report USD; currency normalization is a current limitation before comparing offers in different currencies.

Term definition: a snapshot is not a ledger

last_price optimizes the common current-price read. PricePoint preserves the chronological evidence needed to explain a chart or verify a price-drop decision.

Check

Why keep both history and last_price? History answers temporal questions; the snapshot avoids repeatedly scanning the log for the current card.

Summary

Use UUIDs, database timestamps, Decimal money, constraints, and indexes to make price history correct and queryable.

Module 4 · 17 min

Use asynchronous work and Redis deliberately

After this module, you can explain queue vocabulary, delivery semantics, and Redis’s several roles.

Queue vocabulary

A producer enqueues work, Redis is the broker, a Celery worker consumes it, and Celery Beat produces scheduled refreshes. Queue delivery is at-least-once: a task may run again after a failure boundary, so work must tolerate repeats.

Idempotency and Redis roles

Redis is used as broker, cache, lock store, rate-limit state, shared metrics store, pub/sub transport for live updates, and model-generation quota counter. A per-offer lock using SET NX EX reduces duplicate concurrent refreshes; the database unique constraint is the final integrity backstop.

Best-deal reads use cache-aside: read a cache key, compute and store the result on a miss, then invalidate or expire it when price data changes.

Blast radius trade-off

A single Redis service simplifies a learning project, but an outage can affect queueing, caching, locks, rate limiting, metrics, and pub/sub together. Separating critical roles is a later resilience decision, not an automatic first step.

Check

What makes at-least-once safe here? Idempotency: repeatable discovery, unique offer identity, append-only observations, and a short-lived per-offer lock.

Summary

Use Celery to move source I/O off requests and design every task for repeat delivery.

Module 5 · 15 min

Make failure behavior explicit

After this module, you can distinguish permanent, throttling, and transient failures without hiding bad prices.

Classify source outcomes

An HTTP 404 or 410 means a listing is delisted: mark it permanently gone and stop refreshing it. HTTP 429 means backpressure; do not immediately retry into a provider quota storm. A transient timeout or provider error can use exponential retry.

Exhaustion and partial work

After retries are exhausted, record a dead letter and mark the offer stale so its old price is not trusted. Discovery can have partial failure: return offers from healthy sources and surface failed sources instead of discarding useful results. Alert debounce prevents repeated notifications inside a cooldown.

Commit boundaries

The notification path uses post-send commit behavior: only record the debounce anchor after a successful send. That avoids suppressing a notification merely because state was written before delivery failed, while accepting that distributed delivery still needs careful idempotency reasoning.

Trade-off: a retry is not a promise

Retries improve the chance that temporary failure clears. They do not make provider data trustworthy forever, which is why exhausted work must become explicit stale state rather than an invisible loop.

Check

Contrast a 404 with a transient timeout. The first is a durable listing fact; the second is evidence to retry with bounded exponential delay.

Summary

Classify failures, preserve partial usefulness, avoid retry storms, and make stale data visibly untrusted.

Module 6 · 15 min

Connect API, security, and interface choices

After this module, you can describe FastAPI boundaries and browser-facing security without conflating authentication and authorization.

Security boundaries

FastAPI dependencies resolve a session and current user. Authentication answers who a request represents; authorization answers whether that user may access a row. The browser session is an httponly cookie carrying a JWT. Passwords use bcrypt hashing, while API tokens are stored as a SHA-256 digest and shown in plaintext only once.

Owner-scoped lookup intentionally returns not-found behavior for another user’s item, reducing object enumeration rather than revealing that an inaccessible id exists.

UI delivery

The web app is FastAPI plus Jinja templates and HTMX fragments, avoiding a separate browser build. This is a good fit for a compact, server-rendered product where the API and HTML share domain rules.

Live-update trade-off

Earlier pages used polling. Server-sent events are a one-way server-to-browser stream for price and model progress, simpler than WebSockets when the browser does not need a bidirectional live protocol. Polling is simpler to operate for low-frequency updates; WebSockets are appropriate when interactive two-way messages are required.

Check

Give one example of authorization after authentication: a valid JWT is insufficient unless the requested tracked product belongs to that user.

Summary

Dependencies provide request boundaries, owner checks enforce access, and SSE adds live server updates without a full socket protocol.

Module 7 · 12 min

Discuss AI features and MCP safely

After this module, you can explain optional AI workflows and the user boundary around remote tools.

Optional AI features

Screenshot identification is configuration-gated: an image can be interpreted into a title and search query before it enters the existing pipeline. Meshy generation is also configuration-gated and asynchronous: a Celery task turns a product image into downloadable GLB and USDZ assets, with live progress.

A per-item model row is cache-once by design, and a monthly quota bounds paid generation. This design fails closed when the key is absent and does not require every user to wait for a model.

MCP boundary

The MCP endpoint uses Streamable HTTP and bearer-token authentication. Its six tools are list_wishlist, add_tracked_product, get_best_deal, get_price_history, search_deals, and create_alert. Per-user tool isolation comes from resolving the token to a user and passing that user into service calls.

Storage limitation

Generated files use a shared filesystem volume in the current deployment. That is workable on one host but becomes a filesystem scaling limitation when web and workers do not share a disk; object storage is the next step.

Check

Why is an MCP token not enough by itself? Each tool still needs a user-scoped database operation so one token cannot expose another user’s wishlist.

Summary

Gate optional AI work, bound its cost, and treat MCP as another authenticated interface to the same user-owned data.

Module 8 · 22 min

Walk through AWS and CI/CD choices

After this module, you can defend the compact AWS deployment and name its operational limits.

Request and network path

An Elastic IP reaches Caddy on a public EC2 instance, which proxies to FastAPI in Docker. PostgreSQL runs in private RDS subnets and Redis in private ElastiCache subnets. Security-group references allow the web security group to reach those stores; the design has no SSH ingress because Systems Manager (SSM) provides administration.

Build and deploy

GitHub Actions uses GitHub OIDC to assume a narrowly scoped AWS role, builds the image, pushes it to ECR, and sends a deploy command through SSM. The host pulls the image, runs database migrations, starts the compose services, and a health smoke test checks the public health endpoint. Parameter Store supplies application secrets to the instance role.

Terraform state and deliberate limits

Terraform state is configured for S3 with DynamoDB locking. The small deployment omits a NAT gateway and an ALB to reduce cost and moving parts: private databases need no outbound internet path, while the single public host is the ingress point. That also means fewer availability guarantees.

Deploying an image tag named latest has a consistency risk if a host pulls at an unexpected moment; an immutable commit tag is safer. The workflow has no automated rollback, so a failed health check needs an explicit recovery procedure.

Check

Why is GitHub OIDC preferable to a long-lived cloud key in CI? It exchanges a short-lived identity token for a role under repository and branch conditions.

Summary

This is a cost-conscious single-host deployment with private data services, SSM administration, ECR delivery, and clearly named rollout risks.

Module 9 · 15 min

Scale from evidence, not fashion

After this module, you can give a staged scaling answer tied to observed bottlenecks.

Measure first

Watch queue depth and task latency, database load, Redis memory, and provider quotas. Those measurements reveal whether the bottleneck is worker capacity, a slow query, cache pressure, or a source limit that more workers would make worse.

Name today’s risk

The public EC2 host, single Redis node, and non-Multi-AZ database create a single point of failure. For 10x demand, separate web and worker processes onto independently sized compute while retaining the existing domain boundaries.

Describe 100x only when needed

At 100x, move to ECS behind an ALB with autoscaling, use Multi-AZ managed data services, and put generated model files in S3. Microservices are not the first step: the current API, worker, and source boundaries already isolate the important responsibilities, and distributed service coordination adds cost before evidence demands it.

Check

A provider is returning 429 responses while the queue grows. Which metric changes your plan first: worker count, provider quota, or query latency? Explain why quota and backpressure lead.

Summary

Scale the measured constraint, separate web from workers at 10x, and reserve ECS, ALB, autoscaling, Multi-AZ, and S3 for the 100x case.

Module 10 · 25 min

Rehearse new-grad engineering fundamentals

After this module, you can connect core CS and web concepts to a real Deal Hunter decision.

Data structures and Big O

A hash map gives expected O(1) lookup for source registry entries or an offer keyed by identity. A list preserves an ordered set of offers or price points; a set deduplicates source names; a queue represents pending Celery work; and a heap would efficiently retain the cheapest offers. State the Big O and the real component, not just a textbook definition.

Database fundamentals

An index accelerates lookups such as price history by offer and observation time. Joins combine offers with price points for a best-deal query. A transaction groups a worker’s related writes, while constraints preserve offer identity. Watch for N+1 when rendering products and their offers; select-in loading is used to reduce that pattern.

Network and operating-system fundamentals

HTTP carries browser and provider requests; DNS resolves a host name; TLS protects the connection; status codes distinguish success, client error, and server error; and timeouts stop a provider call from blocking forever. A process has its own address space, while a thread shares one process’s memory. A race condition can occur when two workers refresh one offer, so the system uses a lock; careless lock ordering can cause deadlock.

Price-source network calls are I/O-bound, which fits asynchronous/background concurrency. CPU-bound work competes for processor time and would need a different capacity plan than mostly I/O-bound fetching.

Check

Choose the right concept for each Deal Hunter component: source registry—hash map; refresh broker—queue; unique offer identity—constraint; a competing refresh—race condition and lock.

Summary

Definitions become persuasive when every Big O, transaction, protocol, and concurrency concept is tied to a working component.

Module 11 · 20 min

Practice concise, evidence-based answers

After this module, you can answer likely technical and behavioral questions without overclaiming.

Fifteen technical prompts

1. Why is FastAPI thin?

It validates and persists fast user-facing requests; source calls run in Celery because they are slow and unreliable.

2. What does PriceSource buy you?

It gives every adapter one search/fetch boundary that returns NormalizedOffer, so the pipeline is independent of provider implementation.

3. Why Decimal?

Numeric and Decimal avoid float rounding errors in money comparisons.

4. Why append-only price history?

It preserves observations for charts and lowest-in-window queries; last_price is only a current snapshot.

5. How is discovery idempotent?

A unique offer identity and upsert logic prevent repeat discovery from creating duplicates.

6. What does at-least-once mean?

A task can run more than once, so locks, constraints, and repeat-safe operations are required.

7. Why Redis?

It is the broker plus cache, lock, rate-limit, metrics, pub/sub, and quota store; that convenience also enlarges outage blast radius.

8. How do you handle 404, 410, and 429?

Delist 404/410 offers, treat 429 as backpressure, and reserve exponential retry for transient failures.

9. What happens after retries fail?

Create a dead letter and mark the offer stale so an old value is not presented as reliable.

10. Authentication versus authorization?

Authentication identifies the caller; authorization verifies ownership before returning a product or model.

11. Why store API-token digests?

SHA-256 storage limits exposure if the database leaks; plaintext is displayed only at creation.

12. Why SSE instead of WebSockets?

Prices and generation progress flow one way to the browser, so server-sent events are simpler than a bidirectional protocol.

13. How is MCP isolated per user?

The bearer token resolves to one user, and tools invoke user-scoped service functions.

14. What does the AWS deployment protect?

RDS and ElastiCache are private, security groups reference the web host, and SSM replaces SSH.

15. What is your first scaling move?

Measure queue depth, latency, database load, Redis memory, and provider quotas, then separate web and workers before introducing microservices.

  3. Describe a trade-off, using Redis convenience versus blast radius.

  5. Describe a mistake or limitation, using raw-currency comparison, single-host availability, or missing automated rollback.

Use STAR: situation, task, action, result. For behavioral answers, distinguish a repository outcome from a production customer metric you did not measure.

Avoid overclaiming

  • Do not say the system handles real scale; say which measurements and changes you would use at 10x or 100x.
  • Do not say every source is reliable; name config gates, rate limits, partial failures, and the current currency limitation.
  • Do not claim a team decision as your own; state exactly what you implemented or would validate.
